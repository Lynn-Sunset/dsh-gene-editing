# 给接手 AI 的中文实施说明

## 1. 先理解目标

用户希望能通过 Gene 调节模型看待问题和展开思考的方式。探索可以带来意外方向，创造可以改变组合方式，深度可以让模型多关注机制；它们不需要共同服从一个严格的效率或正确率总分。

同样正确的两个回答，依然可能体现不同偏好。一次更长的探索也可能满足用户意图。先理解人想感受到什么变化，再决定控制位置。不要承诺控制模型内部神经元或输出私人思考。

## 2. 先把现有版本跑通

1. 确认 Node.js >= 24.9.0，目标宿主为 `@deepseek-ai/dsh@0.2.1-rc.3`。
2. 执行 `npm ci --ignore-scripts`、`npm run check`。
3. 执行 `npm pack`，用目标 Harness 的 `plugin add` 安装生成的包。
4. 检查中文面板、八个三档滑块、说明按钮、应用和停用。
5. 确认应用不会发消息，普通对话保持原生输入/工具流程，运行中不能重配，恢复/分叉行为正确。

仓库已经包括所需共享源码。`package.json` 保留 `private:true` 以避免误发 npm registry，GitHub Release 安装包仍可以正常构建和使用。

## 3. 修改入口

| 层 | 文件 | 责任 |
| --- | --- | --- |
| 用户交互 | `src/client.jsx` | 通过原生命令 RPC 读写当前会话配置 |
| 三档映射 | `src/gene-levels.js` | 低/中/高对应协议值0/50/100；兼容历史数值 |
| 实际语义 | `shared/public/compact-policy.js` | 将 Gene 编译成具体偏好 |
| 策略封装 | `shared/public/evidence-policy.js` | 普通偏好及显式验证兼容策略 |
| 说明 | `src/gene-help.js` | 中文解释，与实际语义保持一致 |
| 会话 | `src/index.mjs` | 命令、持久化、应用/停用、恢复/分叉 |
| 原生工具 | `src/tool-integration.mjs`、`src/tool-feedback.mjs` | 工具发现、最终结果投影、事件触发与去重 |
| 历史记录 | `src/request-ledger.mjs`、`shared/src/v4/` | 显式验证兼容，不重新加到普通 UI |

`shared/public/core.js` 中保留早期控制器的兼容函数；不要把其中旧的 DEP/effort 或轮次逻辑当作当前普通模式入口。

## 4. 可继续实施的方向

以下是待实施路线，不代表本版本已经具备。根据用户指定范围选择，避免一次重写整个插件。

### A. 让偏好更容易被人感知

先选一个 Gene 和几道开放问题，说明想影响的关注点、联想方向或取舍。查看当前实际指令是否真的表达这个倾向，再改策略与帮助文字。高档表达倾向，不强制“至少三种方案”；低档保留基本能力，不制造故意错误。

探索可以影响是否离开熟悉的问题框架；创造可以影响是否改变组合方式；两者不能简单共享一句“多想几个方案”。Gene 组合也不是把所有句子无限叠长，应允许取舍和相互制约。

### B. 把工具反馈变成有上下文的帮助

当前 `outcomeMetadata` 只理解有限的显式工具契约，其他业务状态保持 `unknown`。可以新增结果适配器注册接口，由工具提供方声明工具名、契约版本、业务状态、产物身份/版本及必要前提。

实施顺序：定义独立契约 → 为一个明确工具编写适配器 → 存储有限元数据 → 根据相关 Gene 和新结果选择短提示 → 验证权限、去重、恢复和结束语义。不要靠扫描 stdout 中的“成功”猜测验证通过，不把某个实验题名写死成产品功能。

0.6.3 已实现有限的事件触发：失败、重复、恢复及声明的内容版本变化，正常成功不追加规则；按实际接纳记录去重。实现与局限见 `docs/OPTIMIZATION_PLAN.md`。后续扩展应先提供可信元数据，不得退回每次 `read` 都追加同一段训令，也不为了表现 Gene 而多执行工具。

### C. 改善体验比较

固定题干、上下文、模型和 effort，只改变所观察的 Gene；使用新会话避免前一次答案影响后一次。保留公开回答与必要的工具轨迹，让人比较“关注了什么、走向哪里、有哪些意外、是否符合自己的意图”。

先记录人的观察和偏好，也允许“没有感觉到差别”。工具数、耗时和目标检查可以帮助解释，不能用总分替代体验。需要重复时保留同配置的自然波动，不能只挑最好的一次。

## 5. 验收分两部分

**工程验收**：构建、原生工具续步、权限、取消、上下文隔离、历史恢复、打包安装和 UI 状态没有回归。自动化测试负责这部分。

**体验验收**：人是否感受到想调节的方向；变化是否有辨识度；用户是否更容易表达意图；是否保留自然探索空间。公开同题比较帮助说明，不要求所有回答更短、更快或更正确。

交付时写清控制点、用户可见变化、已做验证，以及仍然只是设想的部分。不要从集成测试通过推导“思考方式已精准控制”。
